## 1. WHAT WAS BEING BUILT

The product, as derived from code (not docs): a **multi-tenant SaaS platform for service contractors** — one shared platform run by an operator ("provider"), with per-business ("tenant/org") workspaces covering leads → estimates → jobs → invoices → payments, plus add-on industry "vertical packs," a federation system for reselling/connecting instances, and two marketing sites. There are **four apps in `apps/` — and a fifth, older full application still sitting in root `src/`**. That duplication is the single most important structural fact in the repo.

### apps/tenant-app — the tenant (customer business) workspace
- 382 files, ~53,100 LOC; **85 pages, 132 API routes**; 110 of 132 routes reference Prisma (real DB access).
- Route groups show a real CRM/operations surface: dashboard, leads, opportunities, customers/contacts, estimates, jobs, job-costing, schedule, invoices, payments, wallet, recurring-services, subcontractors, time-tracking, communications, documents, agreements, plus a full **cleaning vertical** section (contracts, estimates, inspections, work orders, billing).
- Auth is real: `src/app/api/auth/login/route.ts` (187 lines) does Prisma user lookup, password + TOTP + recovery-code verification, login-history logging, and session-cookie issuance. Break-glass/emergency auth, refresh tokens, device fingerprints all have models and routes.
- **But:** the app carries the repo's heaviest scaffold load — **547 TODO/FIXME markers** (vs 65 in provider-portal), **61 files containing the word "scaffold," 41 files with "Phase 1/Phase 2" TODO blocks**. The admin/AI areas are the worst: e.g. `src/app/(tenant)/admin/feature-flags/page.tsx` opens with "Phase 1: Scaffold with TODO placeholders" followed by 8 TODOs for the actual functionality. Only 34 of 85 pages are in the core `(tenant)` group.
- Completeness impression: **core CRM = real implementation; admin/AI periphery = scaffold**.

### apps/provider-portal — the platform operator's admin
- 467 files, ~54,200 LOC; **46 pages, 198 API routes**; only 90 of 198 routes reference Prisma.
- The most substantial UI in the repo: 27 provider sections (tenant-health, provisioning, incidents, compliance, branding, federation, revenue-intelligence, api-usage, monetization, rbac, observability, …) with large client components — `IncidentsClient.tsx` 1,121 lines, `settings/page.tsx` 906, `LeadsManagementClient.tsx` 845, `ComplianceClient.tsx` 833, `BrandingClient.tsx` 791, `ProvisioningClient.tsx` 731.
- Has its own API middleware stack (composable auth / rate-limit / idempotency / audit wrappers — see `src/lib/api/`), its own Prisma schema and its own seed/migrate scripts. It is the most "engineered" part of the codebase.
- **But:** roughly half its API routes never touch the database, and some are explicit placeholders — `src/app/api/federation/billing/invoice/route.ts` is commented "Phase 1 scaffold: list invoices (placeholder: empty list with filters echoed)" and returns `const invoices: any[] = []`.
- Completeness impression: **real and substantial admin UI over a half-wired backend**.

### apps/marketing-cortiware — product marketing site
- 44 files, ~3,100 LOC. Real pages (home is an 821-line `page.tsx`, pricing, get-started with an email form).
- The industries page self-describes most verticals as placeholders: `{ name: 'Rolloff (Dumpster Rental)', blurb: 'Functional placeholder; expanding next.' }` (`src/app/industries/page.tsx` lines 10–12, same for Fencing and Appliance Rental).

### apps/marketing-robinson — agency marketing site
- 46 files, ~2,000 LOC. A near-duplicate of marketing-cortiware (same industries page with the same "Functional placeholder" copy). Two codebases maintained for one job.

### Root `src/` — a THIRD, older full application (the hidden one)

## 2. DATABASE

Two separate Prisma schemas, two separate databases — this split is real and intentional (README and scripts agree):

**Root `prisma/schema.prisma`** (tenant DB): 2,004 lines, **90 models, 18 enums**.
**`apps/provider-portal/prisma/schema.prisma`** (provider DB): 1,769 lines, **75 models, 19 enums**.
**51 model names exist in both schemas** (User, Org, Lead, Invoice, Subscription, …) — i.e. the two databases duplicate half of each other's domain model, with drift: the root schema alone has the cleaning suite (CleaningContract, CleaningEstimate, CleaningWorkOrder, …), agreements, imports, and tenant billing (TenantSubscription, RecurringInvoice); the portal schema alone has federation/compliance/developer models (FederatedClient, FederationInvoice, ComplianceFramework, DeveloperAPIKey, WebhookEndpoint, SecretsRotationPolicy, …).

- **Main entities:** Org (the tenant), User (+ RbacRole/RbacPermission/RbacUserRole), Lead, Opportunity, Customer, Job (+ JobPhoto, JobTimeline, JobCost, TimeEntry), Estimate (CleaningEstimate), Invoice/InvoiceLine/RecurringInvoice, Payment, Agreement/AgreementTemplate, Subscription/PlanPrice/PricingPlan, AiUsageEvent/AIUsageLog/AIBudget, AuditLog/AuditEvent, FeatureFlag/FeatureModule, VerticalPack.
- **Multi-tenancy approach:** shared-database, row-level tenancy keyed on **`orgId`** — the root schema contains 182 `orgId` occurrences and the portal schema 91 (plus 1 `tenantId`); the `Org` model carries per-tenant configuration (featureFlags Json, brandConfig, activeVerticalPacks, per-org email/SMS/Stripe credentials and subscription state). There is no schema-per-tenant or DB-per-tenant machinery in code.
- **Migrations are real:** root `prisma/migrations/` has **16 migrations** (2025-09-15 `init_mv` → 2025-10-08, including two same-day duplicate-named `lead_manual_fields` migrations 4 minutes apart — a small process smell); the portal has **15 migrations**. Seed files exist (`prisma/seed.ts` 13 KB, `seed-preview.ts`, `seed-marketing-pricing.ts`).
- **Quirk with consequences:** the root generator outputs the Prisma client into `../node_modules/@prisma/client-tenant` — the build literally depends on the layout of the committed `node_modules` folder, one of the ways the dependency folder became "load-bearing" in this repo's habits.
- Extra migration folders are scattered in docs: `docs/Execute/3/Import pack/DB/migrations`, `docs/Execute/importer/importer extension/DB/migrations`, `scripts/migrations/` — importer tooling shipped as documentation attachments.

### Claim-by-claim verification (10 checks)

1. **"All 10 features 100% complete"** (FINAL_STATUS_REPORT.md / COMPLETE_FEATURE_VERIFICATION.md) — **FALSE as stated.** Multiple of the ten are partial or scaffolded per the checks below; the docs' own file-level evidence is wrong in places (claim 2).
2. **SAM.gov Lead Generation — "100% complete," files listed under `apps/tenant-app/`** (COMPLETE_FEATURE_VERIFICATION.md) — **PARTLY.** The feature is real: a 515-line service calling the live SAM.gov API (`src/services/sam-gov.service.ts`) and a 1,221-line UI (`src/app/(app)/leads/sam-gov/SamGovEnhanced.tsx`). But both live in the **root legacy app**. The cited tenant-app paths **do not exist** (`apps/tenant-app/src/services/sam-gov.service.ts` — no such file; no `api/v2/sam-gov/*` routes in tenant-app; no sam-gov code anywhere in tenant-app). The flagship feature was never ported to the current app.
3. **Federation Management — 100%** — **PARTLY.** Federation is genuinely the most-built subsystem: OIDC discovery route, HMAC signing, idempotency and rate-limit middleware, `FederationKey`/`FederatedClient` models, dedicated unit tests. But its billing surface is a placeholder: `apps/provider-portal/src/app/api/federation/billing/invoice/route.ts` returns an empty invoice list and says so in its own comments ("Phase 1 scaffold… Phase 2: fetch from billing provider or database").
4. **Provisioning / Incidents / Compliance / White-label — 100%** — **PARTLY.** The pages and large client components verifiably exist (ProvisioningClient 731 lines, IncidentsClient 1,121, ComplianceClient 833, BrandingClient 791, all under `apps/provider-portal/src/app/provider/…`), and `tenant-health` and `api-usage` sections exist with real API routes (e.g. `api/provider/api-usage/[tenantId]/rate-limit/route.ts`). Depth behind the UI is uneven: only 90 of the portal's 198 API routes touch the database.
5. **"Theme system with 15+ premium themes"** (README, packages/themes) — **TRUE.** `packages/themes/src/theme-registry.ts` defines 18+ named themes (Futuristic Green, Sapphire Blue, Crimson Tech, Cyber Purple, Stripe Clean, Linear Minimal, Notion Warm, Vercel Contrast, Figma Creative, Finance Navy, …) with a real registry/utils implementation (392 LOC).
6. **Vertical packs for ~19 industries** (packages/verticals; README "vertical-specific feature packs") — **FALSE for breadth, TRUE for one.** 17 of 19 pack files are **5-line skeletons**; `packages/verticals/src/packs/hvac.ts` is representative: `estimate: (i:any)=>({ total: 10000, lines:[], warnings:["skeleton"] })` — a hardcoded $100 total with a warning literally reading "skeleton." Only `cleaning.ts` (320 lines) is a real implementation and `rolloff.ts` (39 lines) is a sketch. The marketing sites concede the same ("Functional placeholder; expanding next").
7. **"Route optimization for roll-off/dumpster"** (README, packages/routing) — **PARTLY.** Code exists and runs (`packages/routing/src/engine.ts`: landfill selection + greedy stop ordering), but it is a single ~45-line file whose own comment calls it a "Phase-1 heuristic," using straight-line lat/lon distance — no road distances, no time windows, no real optimization.
8. **"AI-powered… industry-specific AI agents"** (README headline) — **PARTLY, leaning FALSE.** The AI *accounting* is real (AiUsageEvent/AiModelTest models, budget/alert routes, an `aiMeter`), and `src/lib/aiHelper.ts` (656 lines, copied into all three codebases) contains elaborate prompt-shaped logic — but no call to an external model API appears in the tenant app's aiHelper (no OpenAI/Anthropic endpoint usage found); its outputs are template/strategy strings (e.g. `responseTemplate: 'Standard RFP response template'`). The provider portal even ships `api/developer/ai-assistant/generate/route.ts` whose response says "This is a placeholder for AI-generated code."

A new developer following the README fails immediately. (The README architecture section, by contrast, accurately describes the two-schema split and app layout.)

Break-glass accounts, recovery codes, security questions, and device fingerprints are all modeled in the schema and routed.

**Score: 2 TRUE, 5 PARTLY, 3 FALSE** — and the two TRUEs are the narrowest claims checked. ## 6. SALVAGE INPUTS

### (a) Strongest, most real parts worth keeping
1. **The data model.** Two Prisma schemas, 165 models total, 31 real migrations, seed scripts. Whatever happens to the code, this is the most complete, coherent expression of the product's domain (orgs, RBAC, leads→jobs→invoices, subscriptions, verticals, federation) and the hardest asset to recreate.
2. **provider-portal's platform-admin surface** — 27 sections of substantial UI plus a genuinely decent API middleware pattern (composable provider auth / rate limit / idempotency / audit). Roughly half-wired, but the half that exists is the best engineering in the repo.
3. **tenant-app's core CRM** — leads/customers/jobs/invoices/payments/wallet pages with 110 Prisma-backed routes, a real login/TOTP/break-glass auth system, and the **cleaning vertical** end-to-end (models, routes, the one real vertical pack).
4. **Federation plumbing + its tests, and the agreements rule engine + its tests** — the only areas with real unit tests importing real modules; small, focused, portable.
5. **The SAM.gov client** (`src/services/sam-gov.service.ts`) — a real external-API integration, currently stranded in the legacy app.
6. **packages/themes** (18+ themes), **packages/queue**, **packages/auth-service**, **services/worker** — small, real, reusable.

### (b) Scaffolding / illusion
- **17 of 19 vertical packs** — 5-line skeletons returning hardcoded estimates with `warnings:["skeleton"]`.
- **Root `src/` as a whole** — a third, superseded application (~26,800 LOC live + 34,500 LOC in `_disabled/`) that duplicates the other two and is where docs falsely claim features live in tenant-app.
- **The "AI agents" layer** — usage metering and templates wearing an AI label; no live model integration in the tenant app.
- **Federation billing, tenant admin/AI pages, provider routes that never touch the DB** — UI and endpoint shells returning empty or echoed data.
- **The completion literature** — ~120+ churn documents asserting 100% completion of work that measures 40–80%; their file citations are unreliable.
- **Marketing duplication** — two near-identical marketing apps; industries pages that call themselves placeholders.

### (c) "Strip to a working core" path — keep / discard
**Keep:** tenant-app + provider-portal; both Prisma schemas + all migrations + seeds; packages {auth-service, db, kv, queue, themes, ui (merge ui-components into it), agreements, verticals (cleaning pack only), stripe/twilio/resend wrappers}; services/worker (minus dist/); tests/unit + tests/e2e-playwright; the SAM.gov service (ported into tenant-app, where the docs always claimed it was); .github workflows; the durable docs subfolders (api, architecture, federation, runbooks, security) after a verification pass.
